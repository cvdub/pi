#+title: Domain docs

How engineering skills consume this repository's domain documentation while exploring its codebase.

* Before exploring, read these
- =CONTEXT.org= at the repository root.
- Org ADRs under =docs/adr/=.

If these files do not exist, proceed silently. Create them lazily through =/domain-modeling= only when terms or decisions are actually resolved.

* File structure
#+begin_example
/
├── CONTEXT.org
├── docs/adr/
│   ├── 0001-event-sourced-orders.org
│   └── 0002-postgres-for-write-model.org
└── packages/
#+end_example

* Use the glossary's vocabulary
When output names a domain concept—in a Ticket title, refactor proposal, hypothesis, or test name—use the term defined in =CONTEXT.org=. Do not drift to synonyms the glossary explicitly avoids.

If a needed concept is absent, either reconsider language the project does not use or note a real gap for =/domain-modeling=.

* Flag ADR conflicts
Surface any conflict with an existing ADR explicitly rather than silently overriding it.
